# Resume compression

## Establish the length and review contract

Read the user's current instruction, accepted long source and private review ledger. Reuse the initial target page count; ask only if missing whether it is exact, a maximum, or no fixed limit. Record the language, role, content source, exact format baseline and authorized format changes independently. Respect the user's language order and existing workspace.

Distinguish three products:

- **Long resume:** the complete reviewed source of projects, evidence and wording.
- **Compressed resume:** shorter sentences with the substantive projects, facts, decisions and outcomes retained.
- **Target-length short resume:** content selected, merged or deleted from those sources for the agreed role and page limit.

Default to long approval → compression → selection/deletion when needed. Keep one whole project as the working/review unit unless the user authorizes a batch or consolidation. Use [resume-project-review](../resume-project-review/SKILL.md) for complete original/proposed comparisons. Follow the user's explicit approval contract; a waiver allows autonomous execution only for its named steps, scope and round. Record it and keep validation active. Do not carry a compression-round waiver into a later deletion round without authority.

## Shorten each project without stripping it

1. Map every substantive source sentence to a shorter sentence or a justified combined sentence in a private coverage ledger. Retain the title, dates and actual website as applicable. Record source sentence IDs, full source/proposed wording, keywords, numeric facts with units/baselines/periods, causal relationships, merges and review authority.
2. Compress shared qualifiers once. Combine parallel counts, scopes and system names using a readable structure; retain the meaning of each count and its corresponding entity. Merge adjacent bullets that describe one mechanism, while preserving data source → processing/model/storage → delivery and the supported outcome.
3. Remove repeated context, filler, low-value narration and unnecessarily detailed examples. Keep product pain point, ownership, consequential design/technical choices, model/framework/algorithm names, data relationships, choice rationale and material results. Removing these is content selection and belongs in the next stage.
4. Name the central mechanism instead of reciting procedural steps. Preserve explanation and cause/effect: a stack list, slogan or generic “improved experience” does not replace a design. Compressing “compared frameworks and chose a runtime to build a harness” must still convey the selection, runtime, harness and rationale present in the source.
5. Read the complete compressed project for an interviewer: can they understand the user problem, what the person owned, how the product worked and what changed? If not, restore the minimum explanation needed. Check full sentence/keyword/fact coverage before advancing to the next project.

Do not reduce a multi-part platform to a few generic bullets. Keyword checks complement semantic review: correct digits with lost units, reversed relationships or omitted design reasons still fail. Do not add facts, defensive qualifiers, duplicate skill blocks or rejected self-use statements while shortening.

## Preserve layout and formatting

Read [writing and layout](../../references/writing-and-layout.md) before replacing text. Preserve the chosen format baseline's native fonts, sizes, line/paragraph spacing, indentation, alignment, title hierarchy, selective bold, links, icons/photo and header/footer. Apply only the specifically authorized format changes. Keep source text and format baselines recoverable.

Check mapped paragraph/run properties in the actual Word body, not only styles, images or margins. Check that bold and link positions remain meaningful in rewritten wording. For Chinese files, apply [Chinese document quality](../resume-project-review/references/chinese-quality.md), including the user's spacing preference, full text readback and every-page visual inspection. Compare matching source/output sections in the same renderer/viewer to detect drift.

## Measure pages and choose the next stage

Render the complete compressed file using the agreed format and read its actual page count. Record the target and actual count; do not estimate completion from character reduction.

- If the compressed file meets the agreed exact/maximum page count, follow the file-review contract and deliver it directly. A further deletion stage is unnecessary.
- If there is no fixed page count and compressed delivery is the agreed scope, follow that file-review contract and deliver the compressed file.
- If it exceeds the page target, register it as the compressed source and continue the separately authorized selection/deletion stage through [resume-project-review](../resume-project-review/SKILL.md). Keep a deletion ledger with full omitted/merged text, reason, retained evidence and user decision/authority. Prioritize relevance to the target role, distinct contribution and strong evidence; then build and render a separate target-length short candidate.
- If an exact target is not met for another reason, make the necessary content/layout adjustment within the agreed authority and re-render; meet an exact target rather than treating a maximum limit as equivalent.

Use the actual rendered page count as the page acceptance check. Preserve the long and compressed sources. Register each stage, language, format, content version, target/actual pages and authority separately using [approval and versions](../../references/approval-and-versions.md). Keep candidate/publication states distinct from user acceptance; requested Word/PDF approvals remain independent unless explicitly waived or the deliverable changes.

## Reusable package boundary

Private ledgers, page targets, source filenames, excerpts, personal assets and artifact hashes belong in the caller's workspace. This Skill contains only reusable instructions; do not publish the person's resume materials when synchronizing it.
