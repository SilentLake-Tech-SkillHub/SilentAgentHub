# 验收与排障

## 分层验收

| 层级 | 必须证明 | 不能扩大表述 |
|---|---|---|
| 本地 | 配置、建表、form、单测、JS 语法 | 不代表网关接受 |
| 沙箱网关 | POST 后进入支付宝沙箱收银台 | 不代表买家已付款 |
| 沙箱付款 | 沙箱买家付款、查询、单次入账 | 不代表生产通知 |
| 生产连通 | 正式签名查询返回可解释业务错误 | 不代表允许真实扣款 |
| 生产实付 | 异账号付款、`TRADE_SUCCESS`、账本和额度 | 不代表通知已通过 |
| 通知闭环 | signed notify `verified=1/processed=1`、重复重放不重复入账 | 不代表退款/对账完成 |
| 运营闭环 | 退款、撤销、账单下载、日/月对账、告警 | 才能表述完整运营闭环 |

## 已验证的典型问题

### 同账号自付

现象：正式收银台可展示二维码，扫码后报 `AE150003030`。如果买家就是 PID 对应收款账号，换另一实名支付宝买家测试；先查询订单是否存在，确认未扣款后再创建新单。

### 配置检测仍显示未订阅

确认消息订阅方式为 HTTP、应用网关已保存。平台存在同步延迟，等待后重新加载；不要立即删除订阅或重置接入流程。

### signed notify 到达但验签失败

按规则排除 `sign/sign_type`、过滤空值、按键排序，以 `&` 拼接 canonical 原文，再按通知 `charset` 编码为 bytes。`alipay-sdk-python==3.7.1160` 的 `verify_with_rsa` 不能传 Python `str`。

### 同步回跳入账但通知未入账

这是查询兜底成功，不是通知闭环。修复通知后重放同一 signed payload，必须返回 `success`，事件变为 verified/processed，账本行数和用户额度保持不变。

### 已入账但页面余额不更新

支付回跳、窗口重新获得焦点、页面恢复可见时重新请求服务端余额；必须防抖。不要在前端用支付金额直接加余额。

## 上线前最小检查

- 正式 APP ID/PID/密钥匹配，PID 属于正确公司主体。
- `notify_url` 公网 HTTPS、无重定向、无登录、无 WAF 人机验证。
- 无效签名返回 `fail`；合法 signed notify 返回纯文本 `success`。
- 金额、币种、app_id、seller_id、订单号和 trade_no 均校验。
- 同一通知和同步回跳并发到达时只产生一条账本和一次额度增加。
- 生产发布有备份和回滚，真实付款与退款有单独授权。
