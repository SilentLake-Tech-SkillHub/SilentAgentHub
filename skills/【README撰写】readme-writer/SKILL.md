# README 撰写

为任意项目写出"用户视角、图+文、可安全公开"的 README。README 是写给第一次见到这个项目的人看的，不是写给维护者看的。整个工作流有五道门禁，全部通过且用户明确批准后才发布。

| 门禁 | 内容 | 通过标准 |
|---|---|---|
| ① 框架确认 | 只给章节骨架，不给正文 | 用户确认框架 |
| ② 逐节迭代 | 每次只写一节 | 用户确认该节 |
| ③ HTML 预览 | 模拟 GitHub 渲染的完整预览 | 用户过目无异议 |
| ④ 隐私扫描 | 全库文本 + 图片 + Git 历史 | 零敏感残留 |
| ⑤ 发布批准 | commit / push | 用户明确说"推" |

开始前先读 [盘点与事实核对](references/intake-and-facts.md)。写正文前读 [框架与逐节迭代](references/framework-and-iteration.md)。做展示图和打码前读 [图文展示与打码](references/showcase-and-redaction.md)。配生态图标前读 [图标采集](references/icon-sourcing.md)。进入预览与发布阶段前读 [发布门禁](references/publish-gates.md)。

## 工作流七步

### 第 1 步：盘点与事实核对

- 读项目现状：已有 README 的原样输出给用户；没有则盘点目录结构、真实产物、可截图对象，输出事实清单。
- 判定项目类型（技能包 / 工具 / 网站 / 库），决定用哪套框架变体。
- 事实核对：每个将写进 README 的能力主张必须有项目内证据；无证据的主张要么问用户，要么不写。详见 [盘点与事实核对](references/intake-and-facts.md)。

### 第 2 步：框架先行（门禁①）

- 只给章节骨架，不给任何正文。默认框架（技能包/工具类）：

  1. 这是什么？（出身故事钩子 + 能力清单）
  2. 最终成品是什么？（产物表格 + 每个产物一张实拍图）
  3. 我应该准备什么材料？（三步上手）
  4. 我可以在哪些工具上使用？（生态适配：名称+图标，双安装路径）
  5. 使用技巧（怎么指挥 AI / 每类产物怎么用）
  6. FAQ + 边界
  7. 附录：文件结构

- 库、网站等其他类型的变体见 [框架与逐节迭代](references/framework-and-iteration.md)。

### 第 3 步：逐节迭代（门禁②）

- 每次只写一节，给用户，收修改方向，改到确认再进下一节。禁止一次写完全篇再要总评审。
- 用户的口语素材（故事、口癖、强调）优先原样融入，不做过度润色。
- 用户中途的新决定覆盖旧决定时，全文搜索旧表述是否残留。

### 第 4 步：图文展示

- 每个产物类型必须"真实截图 + 一段说明"，缺图就渲染补拍。
- 敏感信息打码：人名、邮箱、账号、课程/客户代码、绝对路径。打码后不写"已打码"类说明。规则见 [图文展示与打码](references/showcase-and-redaction.md)。
- 生态图标只用官方来源，重名产品先向用户确认，规则见 [图标采集](references/icon-sourcing.md)。

### 第 5 步：HTML 预览（门禁③）

- 组装完整 README，生成模拟 GitHub 渲染效果的本地 HTML 给用户过目。预览文件加入目标项目 `.gitignore`，永不入库。

### 第 6 步：隐私与安全扫描（门禁④）

- 全库文本扫描（人名/邮箱/账号/课程或客户代码/绝对路径/组织敏感名）。
- 图片逐张目检打码到位。
- Git 历史扫描：历史提交里的旧泄露与当前文件同等对待；发现泄露时报告用户并给出处置方案（删库重建 / 重写历史），等用户选择。详见 [发布门禁](references/publish-gates.md)。

### 第 7 步：发布（门禁⑤）

- **未经用户明确批准，绝不 commit、绝不 push**——哪怕前四道门禁全部通过。
- 发布后从远端拉回实际内容复扫一遍，确认线上零残留。

## 边界

- 不虚构：README 里每个主张可溯源到项目证据，不写项目做不到的事。
- 不代替用户决定发布：推送、删库、改写历史一律先请示。
- 不接管项目本体：只写 README 和配套图片，不改项目代码（目标项目 `.gitignore` 追加预览文件除外）。
- 不硬套模板：框架按项目类型适配，不把技能包模板套到库或网站上。
- 不写营销号文案：文风是"讲给一个新用户听"，克制、具体、可验证。

## 硬规则（踩过的坑）

1. 专有名词拼写自查：动笔前把产品名、平台名逐个核对（如 Canva 是设计工具，学校系统是 Canvas）。
2. 命名三处一致：文件夹【中文】英文、SKILL.md 的 `name` 字段、仓库名对齐。
3. 承诺句不能自相矛盾：结尾的能力承诺和"边界"声明逐条对照（如"一键解决作业"与"不代写作业"不能同时存在）。
4. 打码坐标必须目检回看，避免糊错行；打码方式优先"渲染层替换文字"，其次模糊，最后裁剪。
5. 图标取回后校验文件真实是图片（HTML 响应不算成功）；重名产品不猜，问用户。
6. 用户改了某一节的表述后，其余节里同一事实的旧表述全部同步。
7. "已打码"、"下图涉及隐私"之类的说明文字不进正文。
8. 预览 HTML、临时截图脚本不入库。
