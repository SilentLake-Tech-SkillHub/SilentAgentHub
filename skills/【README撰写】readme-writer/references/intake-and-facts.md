# 盘点与事实核对

动笔前必须完成本文件的全部清单。没有事实就没有 README。

## 盘点清单

按顺序收集，结果整理成一份"项目事实单"输出给用户确认：

1. **现有 README**（如有）：原样完整输出给用户，不总结、不先改。
2. **一句话定位**：这个项目是什么、给谁用、解决什么问题。定位含糊时先问用户，不猜。
3. **目录结构**：`tree` 或等价清单；识别入口文件（SKILL.md / package.json / index.html 等）。
4. **真实产物清单**：这个项目交付什么（文件夹、网页、文件、命令）。每个产物记下"在哪里能亲眼看到"。
5. **可截图对象**：现成页面/文件 > 需要渲染的 md/HTML > 需要补拍的实景 > 只能示意（必须标注示意）。
6. **目标用户画像**：学生？开发者？客户？决定称呼（你/您）和术语密度。
7. **项目类型判定**：技能包 / 工具 / 网站 / 库 / 内部系统，决定框架变体。
8. **出身故事素材**：问用户"为什么做这个项目"，收集原话。用户的口语叙述是最好的钩子素材。

## 事实核对表

每个将写进 README 的主张登记一行：

| 主张 | 证据位置 | 状态 |
|---|---|---|
| 例：AI 能只读访问课程平台 | skills/xx/SKILL.md 末段"Computer Use 的只读目标" | 已证实 |
| 例：支持导出 PDF | 未找到 | 待问用户 |

规则：

- 状态只有三种：**已证实**（项目内有据可查）、**待问**（问了用户且拿到答复才算证实）、**删除**（无证据且用户不置可否）。
- 口头承诺不算证据；版本号、数字、百分比取当前实际值，不取宣传值。
- "待问"的主张在框架确认阶段一并问掉，不带着疑问进正文。
- 用户答复与项目证据冲突时，向用户指出冲突，由用户裁决，不自行取舍。

## 输出

盘点完成后向用户交付两样：项目事实单 + 拟采用的框架骨架。两者都确认后才进入逐节写作。
