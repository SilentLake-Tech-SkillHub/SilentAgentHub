# 发布门禁

五道门禁全部通过 + 用户明确批准，才允许发布。任何一道没过就停在那一道。

## 门禁③：HTML 预览

- 组装完整 README 后，生成模拟 GitHub 渲染效果的本地 HTML：
  - 白底、居中版心（max-width ~1012px）、GitHub 字号与分隔线样式、表格边框、代码块灰底；
  - 图片用相对路径引用真实文件，图标按最终尺寸内嵌；
  - 顶部加一条提示条"本地预览 · 尚未推送"。
- 在浏览器打开给用户过目；预览文件名固定 `README-preview.html`，加入目标项目 `.gitignore`，**永不入库**。
- 用户在预览里提出的修改照常走逐节迭代，改完重新生成预览。

## 门禁④：隐私与安全扫描

发布前对目标项目做三扫：

**1. 全库文本扫描**（排除 `.git`、预览文件）：

```
人名与账号：   作者本名、用户名、账号昵称
联系方式：     [a-z0-9._]+@[a-z0-9.-]+（任何邮箱）
标识代码：     课程/客户/内部项目代码（如 CA\d{4} 这类模式）
路径：         /Users/、/Volumes/、C:\Users\
机构敏感名：   未公开的组织、部门、讲师/客户姓名
日期与数字：   精确到天的个人日程、真实成绩
```

命中逐条判定：产品命名（如仓库名本身的 ntu）保留；个人/课程/客户信息泛化（CA6000→CAXXXX）或删除。

**2. 图片目检**：逐张放大检查打码区域，对照打码记录确认无漏网。

**3. Git 历史扫描**：对每个历史提交 grep 同一套词表。历史里的旧泄露与当前文件**同等对待**——只追加干净提交不等于清理。

历史有泄露时的处置方案，报告用户并等其选择：

- **方案 A 删库重建（最彻底）**：保存仓库描述 → 本地重建单提交历史 → `gh repo delete` → 重建 → 推送。旧 SHA 彻底消失。适用于无 star/fork/协作者的仓库。
- **方案 B 重写历史强推**：git filter-repo 替换敏感词后 force push。保留提交形状，但 GitHub 对旧提交有缓存，彻底性次于 A。

## 门禁⑤：发布批准

**红线：未经用户明确说"推"/"发布"/"可以推"，绝不执行 `git commit`、`git push`、`gh repo create/delete`。** 前四道门禁全过也不构成发布授权；"用户看过预览"不等于"用户批准发布"。

发布流程：

1. 用户批准 → commit（信息概括本次 README 变更）→ push；
2. 若走了方案 A：先取旧仓库描述，重建后原样配回；
3. **发布后回归验证**：从远端拉回实际内容（tarball/API），重跑文本扫描，确认线上零残留；
4. 向用户报告：线上链接、提交号、验证结果。

## 交付物清单

发布完成时向用户交付：线上 URL、README 最终版位置、新增图片清单、打码记录位置、（若有）历史清理方案及执行结果。
